<Context>
The greatest benefit of using Git is that it makes it safe to experiment. If you write terrible code, you can just throw it away and go back to your last known good commit. But to do this safely, you must be very clear about *which* changes you are throwing away.
</Context>

<Objective>
By the end of this lesson, you will discard uncommitted changes and unstage files safely.
</Objective>

<Concept>
## Unstaging a File
Sometimes you run `git add` by mistake. You don't want to lose your work; you just want to take the file *out* of the Staging Area before you commit.

Use the `git restore --staged` command:
```bash
git restore --staged index.html
```
This moves `index.html` back to the Working Directory. Your code is perfectly safe, it just won't be included in the next commit.

## Discarding Changes Completely
Sometimes you experiment with a file and completely break it. You want to throw away your recent edits and go back to exactly what the file looked like in the last commit.

Use the `git restore` command (without `--staged`):
```bash
git restore index.html
```
**WARNING**: This is destructive! Git will permanently delete the changes you made to `index.html` since the last commit. You cannot get them back.
</Concept>

<InteractiveSandbox type="terminal_debugging">
You are working on a website. You just typed some experimental code into `app.js` and saved it. 
You ran `git add app.js` by accident! 

1. Run the command to remove `app.js` from the Staging Area.
2. After checking your code, you decide the experiment was a failure. Run the command to completely discard your edits to `app.js`.
</InteractiveSandbox>

<HintLadder>
- Level 1: First, how do you pull a file back out of the Staging Area?
- Level 2: Use `git restore --staged app.js`
- Level 3: Now the file is back in the Working Directory. How do you throw away the changes entirely?
- Level 4: Use `git restore app.js`
</HintLadder>

<IndependentPractice>
1. Modify a file in your project.
2. Run `git status` to see the change in your Working Directory.
3. Run the destructive command to discard those changes and reset the file to the last commit.
4. Run `git status` again. What does it say?
</IndependentPractice>

<Reflection>
Always run `git status` before restoring anything! You must know exactly what state your files are in before you tell Git to throw away your work.
</Reflection>
