<Context>
You have learned HTML, CSS, JavaScript, and Git. Now it is time to build something entirely from scratch. You will not follow a step-by-step tutorial. You will act as a developer, starting with the most important step: defining what exactly you are going to build.
</Context>

<Objective>
By the end of this lesson, you will define a clear, solvable problem and identify the target audience for your capstone project.
</Objective>

<Concept>
## The Importance of Scope
A developer's greatest enemy is "feature creep"—the tendency to keep adding ideas until a project becomes impossible to finish. To prevent this, you must define strict boundaries.

## The Requirements Framework
A professional project definition separates requirements into three buckets:
1. **Must Have**: The absolute core features. If these are missing, the project fails.
2. **Should Have**: Important features that make the project good, but could be skipped if time runs out.
3. **Could Have**: "Nice to have" bonus features you will only build if everything else is finished early.

## Defining the Audience
Who is this project for? If you say "everyone," you are designing for no one. A clear audience dictates design decisions. A website for accountants will look very different from a website for kindergarteners.
</Concept>

<InteractiveSandbox type="classification">
A developer is building a simple To-Do List application for students. Classify the following features:

A. The ability to add a text item to a list.
B. An AI integration that predicts what the student will type next.
C. The ability to delete an item from the list.
D. A dark mode color theme toggle.
</InteractiveSandbox>

<Feedback>
A and C are "Must Haves"—a To-Do list is useless if you cannot add or delete items. D is a "Should Have" or "Could Have". B is a massive "Could Have" that would likely derail a simple project!
</Feedback>

<IndependentPractice>
Create a new file in your Capstone repository called `README.md`. Inside it, answer the following questions:

1. **What is the problem you are solving?**
2. **Who is the target audience?**
3. **Must Have**: List exactly 3 features that are absolutely required.
4. **Should Have**: List 1 or 2 features you hope to include.
5. **Could Have**: List 1 bonus feature.

Commit this `README.md` to your repository using Git!
</IndependentPractice>

<Reflection>
By committing your requirements to your repository, you have created a contract with yourself. If you get distracted by a shiny new feature next week, you can look at your `README.md` and say, "No, that is not in the Must Haves."
</Reflection>
